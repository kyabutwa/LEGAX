# LegaX — Production UI Implementation\n\n## 33 — Control-Plane UI Foundation\n\n**Status:** Implemented foundation; domain data surfaces remain fail-closed until their canonical read/authorization dependencies are live.\n\n### 1. Implementation protocol\n\nThis implementation follows:\n\n**01–32 review → repository inspection → runtime/UI/database inspection → contract comparison → targeted research → implementation → test → inspect → fix → re-test → deploy → live verification**\n\nThis is an implementation phase, not another architecture-only document.\n\n### 2. Product surface\n\nThe root experience is now the LegaX control plane:\n\n**LegaX** → Identity → People → Participation / Context → Communities → Organizations → Providers → Places → Units → Resources → LegaServices → Access → Requests / Actions → Activity / Events → Evidence → Commerce → Account → Administration\n\nThese are separate governed surfaces, not a generic administration dashboard.\n\n### 3. Shared shell\n\nThe shared shell provides persistent LegaX navigation, mobile-first responsive behavior, accessible navigation and focus states, reduced-motion support, Account entry point, repository logo asset (IMG_1700.jpeg), floating layered cards, high-contrast text tokens, and responsive conversion from dense grids to focused mobile cards.\n\nThe visual language is inspired by the spatial discipline of modern iPhone system surfaces: depth, hierarchy, radius, translucency and focused cards. It is not an Apple clone and does not change LegaX semantics.\n\n### 4. Logo handling\n\nIMG_1700.jpeg is the canonical repository logo asset supplied for this UI implementation.\n\nThe UI places the logo in the global mark and root hero and uses a dark-surface compositing treatment so the asset visually integrates with the shell. A true pixel-level transparent PNG conversion is deliberately not claimed here because the repository asset is JPEG and the runtime implementation does not have an image-processing pipeline.\n\n### 5. Governed data rule\n\nA surface must not fabricate domain records.\n\nWhen its authoritative read/context/authorization dependencies are unavailable, it presents:\n\n**No authoritative records are loaded into this surface.**\n\nThis is a valid governed state, not a failure to fill the screen.\n\n### 6. People state machine\n\nThe People surface is aligned to:\n\n**Context selected → Authorized read → People records → Identity/evidence state → Relationship / participation → Available governed actions**\n\nInvariant:\n\n**VISIBLE ≠ AUTHORIZED**\n\nParticipation, relationship or visibility cannot manufacture permission.\n\n### 7. Service state machine\n\nLegaServices is aligned to:\n\n**Service → Request → Eligibility / capability → Authorization → Execution → Outcome → Evidence / event**\n\nUnknown external outcome is never rendered as success.\n\n### 8. Places state machine\n\nPhysical-world navigation is aligned to:\n\n**Community → Place → Unit / facility → Resource → occupancy / relationship / access state**\n\nLocation is context, not authority. Occupancy is not ownership. Availability is not automatic assignability.\n\n### 9. Community / Organization / Provider separation\n\n20A Communities: community life, people, places, participation, visitors, shared services and community operations.\n\n20B Organizations: purpose, governance, teams, decisions, work, projects, resources, policies and assurance.\n\n20C Providers: service catalog, customers, workforce, capacity, dispatch, work orders, resources, commerce, quality and reconciliation.\n\nThey share LegaX core contracts but do not collapse into one generic admin UI.\n\n### 10. Authority boundary\n\nThe UI presents authority; it does not create authority.\n\nThe UI never becomes an authorization engine, execution engine, source of truth, replacement for server-side policy, or parallel identity authority.\n\nClient-side visibility is never a security boundary.\n\n### 11. Visual accessibility rule\n\nDark surfaces use light readable text. Light surfaces use dark readable text. Accent colors communicate state or orientation and are never the only state indicator.\n\nThe implementation includes visible keyboard focus, semantic navigation, responsive reflow, reduced motion, readable contrast-oriented surface tokens, accessible empty/status regions, and no critical information conveyed only through color.\n\n### 12. Testing\n\nSmoke tests cover canonical fail-closed runtime invariants, all control-plane surface routes, shared shell and logo reference, governed empty-state language, authority boundary language, reduced-motion/accessibility hooks, and legacy product-name exclusion.\n\nFurther E2E verification must validate live browser rendering and the eventual authoritative data/authorization integrations.\n\n### 13. Conformance boundary\n\nThis implementation is not a claim that every domain capability is implemented.\n\nIt establishes the production UI foundation and governed surfaces while preserving the Phase 30 rule:\n\n**No evidence → no verified conformance claim.**\n\nThe UI foundation is implemented; domain execution remains bounded by its canonical runtime dependencies.
